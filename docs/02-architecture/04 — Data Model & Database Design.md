# 1. DESIGN PRINCIPLES

| # | Principle | Source |
|---|---|---|
| P1 | **UUID primary keys**, generated by the application (UUID v7 recommended for index locality); the database never derives meaning from an id | — |
| P2 | Every instant is `timestamptz` (UTC). A local wall-clock concept is stored as `timestamp` **only** next to its IANA zone (`operating_session.local_start/local_end` + `timezone`, the Booking session snapshot) | `NFR-07`, `NFR-08` |
| P3 | Every interval is a half-open `tstzrange` `[start, end)` derived from its start/end columns and checked by constraint | `FR-AVL-15` |
| P4 | Money is `NUMERIC(12,2)` EGP; never floating point; price math is enforced by `CHECK` (`venue_price_total = round(hourly × minutes / 60, 2)`) | `NFR-25`, `ADR-017` |
| P5 | Product-visible closed value sets are `text` columns with a **closed `CHECK` list** spelled exactly as the FRS spells them (not PostgreSQL `ENUM` types) — unknown values are rejected at write time and the list is visible in the model | `NFR-23`, `ADR-016`, `ADR-027` |
| P6 | Historical values are **snapshot columns on the owning row** and are immutable after creation (guard triggers) | `FR-AUD-01`, `I6` |
| P7 | Append-only tables carry a guard trigger **and** revoked `UPDATE`/`DELETE`/`TRUNCATE` for runtime roles | `NFR-22`, `ADR-008` |
| P8 | Foreign keys everywhere, including across module schemas; `ON DELETE RESTRICT` for everything historical; every foreign key has a supporting index | `FR-ACC-08` |
| P9 | No hard deletion where history is required. Account deletion is O19 anonymisation in place (`iam.anonymise_user`) | `FR-ACC-10`, PCR-002 |
| P10 | Every terminal Booking (`REJECTED`/`CANCELLED`) and Tournament (`REJECTED`/`CANCELLED`) row carries exactly one reason from its closed list | `NFR-26`, `I3` |
| P11 | Every revenue-producing record carries `business_date` | `FR-AVL-14`, `FR-AUD-07` |
| P12 | One schema per owning module (§3). A module's schema is written only by that module's code or by that module's producer functions | `03 §2`, `ADR-027` |

# 2. ENFORCEMENT MODEL (`ADR-026`)

The database is not a passive store. It owns the invariants that must hold no matter which code path writes; the application owns decisions. The split:

| The database owns (guard triggers, constraints, producers) | The application owns |
|---|---|
| Non-overlap of active reservations (`I1`) and of a Customer's Online commitments | The single canonical availability predicate and every eligibility decision (`01 §15` rule 1) — the database re-asserts the parts it can prove, it never replaces the predicate |
| State-machine graphs and terminal immutability: Booking (`booking.guard_booking_transition`), Tournament, Participant, Review, Emergency, Ban, Verified Player | Which transition to take, and the reason-priority resolution at a boundary (`06`) |
| Closed value sets; exactly one terminal reason (`I3`) | Cascade orchestration order and notifications (`I4`) |
| Snapshot immutability, append-only history and ledgers (`I6`) | Owner Password verification (`I7`) — the database stores only the secret and the audited outcome |
| Deadline arithmetic that the Product fixes (`approval_expires_at`, Late Confirm `expires_at`, venue response deadline at creation, OTP validity) | Scheduling the jobs that act on those deadlines (`08`) |
| Deterministic Trust replay results and the one-active-Ban rule (`I5`) | Invoking replay/reconciliation and emitting side effects |
| Anonymisation completeness, deletion-request completion, review removal on deletion | Presenting codes and localisation (the database raises; the API maps to `ApiErrorCode`) |

## 2.1 The command protocol

Every business write runs in **one** `READ COMMITTED` transaction that opens a command context first:

1. `tournament.begin_command(users[], venues[], resources[], tournaments[], new_tournaments[])` — or `admin.begin_command(admin, correlation, users[], venues[])` for Platform Admin commands, or the Trust/Loyalty equivalents. It discovers the full lock set and takes row locks in the fixed order **Users → commitment guards → Venues → Venue Accounts → Resources → Tournaments → Bookings → Attendance → Late Confirmations → Reservations → Bans → Trust projections**, then samples the command instant once. A changed lock set raises SQLSTATE `40001` and the whole transaction is retried.
2. The command's DML runs. Guard triggers evaluate time at the command instant (`tournament.command_now()`) or the transaction timestamp — never a client-supplied clock.
3. Tables that only a producer may write (`account_deletion_request`, `review_report`, `review`, `account_anonymisation`, `username_change`, configuration, ledgers …) require a **private write token**: the producer calls `technical.enter_write(table, key)` … `technical.leave_write(token)`; a guard calls `technical.require_write`. Application code calls the producer function instead of writing the table.
4. **Deferred constraint triggers** check cross-row completeness at `COMMIT` (Tournament aggregate, attendance integrity, loyalty source integrity, anonymisation completeness). A command that leaves a half-done cascade cannot commit.

Isolation: `READ COMMITTED` only. `tournament.begin_command` refuses anything else and the inventory cross-class guard refuses `REPEATABLE READ`.

# 4. KEY MECHANISMS

## 4.1 Inventory — the reservation ledger (`ADR-003`, `ADR-010`, `05 §3`)

`inventory.resource_reservation` is the exclusive occupancy ledger. One row per held interval; `reservation_type` ∈ `BOOKING` · `LATE_CONFIRM_HOLD` · `TOURNAMENT_APPROVAL_HOLD` · `TOURNAMENT_HOLD` · `MAINTENANCE` · `CLOSURE`, with exactly one owner column set (`ck_reservation_owner_shape`).

- `planned_start`, `planned_end`, `planned_range` are immutable after insert (`FR-AVL-13`).
- A row is **active** while `active_flag = true`. Release is one-way: `active_flag = false`, `actual_reservation_release_at` and `release_reason` recorded once. A released row is never re-activated; a new hold is a new row (Late Confirm, Tournament approval → Tournament hold).
- **`ex_no_double_booking`** — `EXCLUDE USING gist (resource_id WITH =, planned_range WITH &&) WHERE active_flag AND reservation_type <> 'MAINTENANCE'` — is invariant `I1` for Bookings, holds and Closures.
- **Maintenance** is excluded from that constraint because the Product lets Maintenance overlap Maintenance (`FR-OPS-03`) and lets a Closure overlap Maintenance (`FR-VEN-33`). The cross-class guard `inventory.guard_resource_reservation_cross_class` serialises on the Resource row and refuses: Maintenance over any non-Maintenance reservation, a Closure over a commitment or another Closure, and any commitment over anything active. Race safety rests on `READ COMMITTED` re-reads after the lock (§2.1).
- Actual occupancy of a row is `[actual_reservation_start, COALESCE(actual_reservation_release_at, planned_end))`. A no-show releases the row at the no-show instant, so the remaining interval is immediately sellable (`FR-AVL-12`); the planned interval is never rewritten.
- Venue Emergency Closure, Resource Emergency Outage and Operational Selling Blocks are **not** ledger rows; they live in `operations.emergency`, `venue.venue_selling_block`, `resource.resource_selling_block` and are non-exclusive blocking inputs to the predicate (Layer 2).

## 4.2 Customer commitments

`booking.booking.commitment_period` is derived by trigger for Online Bookings in `PENDING` · `AWAITING_CUSTOMER_CONFIRMATION` · `CONFIRMED` · `ACTIVE` and is `NULL` otherwise. `ex_customer_no_overlap` makes overlapping Online commitments impossible (`FR-BOK-04`); the four-commitment limit is counted under the `iam.user_commitment_guard` row lock (`FR-BOK-03`). Every User gets its guard row automatically on insert.

## 4.3 Booking

- Snapshots (price, fee, session, business date, resource name/console) are immutable after insert.
- Creation guards: Online Bookings are created `PENDING` at an `ACTIVE` Venue with an `ENABLED` Venue Account and an `ACTIVE` Area, inside the current Operating Session and before its final 10 minutes, at least 15 minutes before Start, with `venue_response_expires_at = created_at + 10 minutes` and `booking_fee_snapshot` = the Global Booking Fee effective at creation. Manual Bookings need an `ENABLED` Venue Account, a non-`ONBOARDING` Venue, and are never back-dated (`CONFIRMED` future or `ACTIVE` walk-in at the creation instant).
- **State machine** (`booking.guard_booking_transition`): exactly the FRS §2.1 graph, the permitted terminal reasons per source state, Customer cancellation only before Start, No-show reversal → `CANCELLED/ADMIN_NO_SHOW_REVERSAL` before the original `endAt` and → `COMPLETED` after it, and terminal immutability.
- `booking.booking_history` is append-only; `STATUS_TRANSITION` rows carry the reason, `BOOKING_EVENT` rows carry one of the 12 Booking Events and the scoped `detail_code`.
- Late Confirmation: `booking.late_confirmation` with `expires_at = LEAST(initiated_at + 5 minutes, startAt)`, one open attempt per Booking (`ux_lc_open`), its own hold row in the ledger.
- Emergency pauses: `operations.booking_timer_pause_history` and the four pause columns on `booking.booking`, each counter capped at 30 minutes.

## 4.4 Tournament

- `ck_tournament_capacity` 8–32; `ck_tournament_duration` ≥ 60 minutes in 30-minute steps; `ck_tournament_time_arithmetic` (`checkpoint_at = start_at − 1 h`, `created_at ≤ start_at − 2 h` for both host types); `ck_tournament_approval_deadline` (`approval_expires_at = LEAST(created_at + 10 min, checkpoint_at)` for Player-hosted, `NULL` for Venue-hosted).
- Venue Reject → `REJECTED` with `VENUE_REJECTED_TOURNAMENT`; approval timeout → `CANCELLED` with `VENUE_DID_NOT_APPROVE_TOURNAMENT_IN_TIME` (`ck_tournament_rejected_reason`, `FR-TRN-10`). One pending request per Creator (`ux_tournament_one_pending_creator`); 5-minute retry after `REJECTED` or approval timeout.
- Boundary guards evaluate checkpoint/start at the boundary instant even when the worker is late; a BAN-only participant is restored only if the Ban ended strictly before the boundary it is evaluated at (PCR-001, Product §37.11).
- Participants: `INELIGIBLE` carries `ineligible_reason` `BAN` or `ACCOUNT_DELETED` iff the status is `INELIGIBLE`; `tournament.capacity_occupied_count` counts `JOINED` plus still-valid BAN-only reserved slots.

## 4.5 Trust, Verified Player and Bans

`trust.trust_event` is the append-only input stream (11 event types). `trust.replay_timeline` derives counters, penalty stage (thresholds 3/2/2/3, durations 7 days / 1 month / 2 months), completed-attended count and Verified Player qualification (10 Completed Bookings); `trust.trust_projection` is the synchronous projection with checkpoints in `trust.trust_projection_checkpoint`. `trust.ban_qualification` / `trust.ban_qualification_consumption` / `trust.ban_instance` separate qualification from the operational Ban; `ux_one_active_ban` allows one `ACTIVE` Ban per User. Cascades are registered once per Ban (`trust.ban_cascade_booking_target`, `trust.ban_cascade_reservation_target`, `trust.cascade_execution`). Verified Player transitions are `trust.verified_player_transition` with a unique `transition_id`.

## 4.6 Loyalty, fees and configuration

Points and Wallet are append-only ledgers (`loyalty.points_transaction`, `loyalty.wallet_transaction`; since v1.1.39 the Wallet ledger holds Booking Fee refund credits and Booking Fee payment debits, PCR-009; since v1.1.40 the Points ledger holds `BOOKING_FEE_PAYMENT` debits and their `BOOKING_FEE_REFUND` credits, and `loyalty.booking_fee_points_payment` records what Points paid of each fee, PCR-010) with non-negative balances and `UNRECOVERED_REVERSAL_AMOUNT` audit for capped reversals. Reward values are read from versioned configuration at the Product's anchor instant and stored on the transaction (`loyalty.reward_application`).

Configuration (`ADR-028`): `config.configuration_key` (registry, append-only) · `config.configuration_version` (append-only history with `effective_from`) · `config.system_configuration` (current value). Launch keys: `booking.fee` (EGP 0), `tournament.creation_fee` (EGP 0), `loyalty.attended_points` (200), `loyalty.referral_points` (1000), `loyalty.wallet_refunds_enabled` (false); since v1.1.40 (PCR-010) `booking.fee_mode` (`PER_BOOKING`), `booking.fee_per_hour` (EGP 0) and `loyalty.points_per_fee_unit` (10,000, even). `config.effective_numeric(key, at)` / `config.effective_text(key, at)` return the value effective at an instant; Tournament creation checks its fee snapshot against it, and Booking creation against `config.booking_fee_for(nominalMinutes, at)` — the per-booking fee, or the per-hour fee × nominal minutes / 60 rounded half-up to 2 decimals.

## 4.7 Identity, deletion and reviews

- `iam.user_account`: `phone_e164` unique; username unique on `lower(btrim(username))` among non-anonymised accounts; 30-day username cooldown with automatic `iam.username_change` history.
- OTP: `iam.otp_challenge.issued_at`; validity exactly 5 minutes; at most 5 attempts; resend after 60 seconds per destination and purpose; at most 5 sends per destination per hour; a new OTP supersedes the open one.
- Account deletion (PCR-002): `iam.request_account_deletion` creates/reuses one open `iam.account_deletion_request`; `iam.anonymise_user` (O19) writes `iam.account_anonymisation`, blanks PII (phone tombstoned as `anonymised:<id>`), revokes Customer refresh tokens, removes the User's Reviews from public display, completes the open request and audits. A deferred check refuses to commit an anonymisation that leaves public Reviews, an open request or a live token. Tournament participation is reclassified to `ACCOUNT_DELETED` by the Tournament module in the same transaction (deferred check).
- Venue Marketplace Status: `ONBOARDING` → `ACTIVE`/`INACTIVE`/`SUSPENDED`; the last three switch freely; a Venue never returns to `ONBOARDING` (`venue.guard_venue_marketplace_transition`, `01 §14` A9). An Area cannot be deactivated while it has `ACTIVE`/`SUSPENDED` Venues, and only `ACTIVE` Areas take new assignments.
- Reviews: one current Review per User per Venue (`ux_review_current`), 30-day cooldown after Admin removal, moderation events with mandatory reason. Review reports (PCR-003): one unresolved report per reporter per Review, never a moderation transition.

## 4.8 Scheduling, outbox, idempotency, audit

`technical.scheduled_job` (status `PENDING` → `LEASED` → done, `leased_until`, unique `idempotency_key`), `technical.outbox_event` (transactional outbox, `state`, retries, dead letter), `technical.idempotency_record` (per principal + endpoint + key, request fingerprint, stored response). `audit.audit_event` is append-only with provenance checks, indexed by subject and by correlation id. `admin.admin_alert` holds operational alerts (e.g. the 3-in-30-days tournament cancellation abuse alert).
